## 1. The headline

The host is **much more crowded, and much more idle, than `docs/IMPLEMENTATION-PLAN-POST-M6.md` §7.8 recorded.**

- Crowded: there are **eleven** non-OS units belonging to other products, not two — `brain.service`, `hackathon-review.service`, `cloudflared.service`, plus **eight auxiliary `brain-*` oneshot services driven by seven timers**, four of which fire **every 60 seconds**. There is also a **root cron job** (`/etc/cron.d/brain-backup`) that §7.8 never found, running an encrypt-and-upload pipeline every 6 hours.
- Idle: across **nine days of `sysstat` history**, peak CPU busy was **9.4%** of 2 vCPUs (typical days 1.4–2.8%), peak 1-minute load average **0.34**, and peak non-cache memory in use **431 MB of 3.7 GB**. Global memory PSI is **0.00** on all windows — this host has never been under memory pressure in its recorded history.

Both halves matter. The crowding means "two quiet neighbours" was the wrong mental model and the interaction surface is bigger than assumed. The idleness means the headroom is real and generous, and the ceiling question is less fraught than §7.8 feared.

## 5. Scheduled jobs outside systemd

- **`crontab -l`: empty for both `root` and `brain`.** `/var/spool/cron/crontabs/` contains no user crontabs at all.
- **`/etc/cron.d/brain-backup` — present, and not recorded in §7.8.** Runs `0 */6 * * *` as user `brain`:
  `/opt/brain/scripts/backup-offsite.sh >> /var/log/brain-backup.log 2>&1`
  Its pipeline, per the script's own header and confirmed by reading it: `sqlite3 .backup` → **tmpfs staging at `/run/brain-backup-staging`** → scrub + verify → atomic publish to `/opt/brain/data/backups/` → `gpg --encrypt` → `rclone copyto` to Backblaze B2 → remove volatile stage. `/var/log/brain-backup.log` shows it succeeding on schedule, four times a day, most recently `2026-08-21_1230`.
- `/etc/cron.d/` otherwise: `e2scrub_all`, `sysstat`, `.placeholder` (all stock).
- `/etc/cron.daily/`: `apport`, `apt-compat`, `dpkg`, `logrotate`, `man-db`, `sysstat`. `/etc/cron.weekly/`: `man-db`. Hourly and monthly: empty.
- `atq`: empty (though `atd.service` is running).

### 5.1 The backup job's real resource shape — and its one coupling to Life in Days

`brain.sqlite` is **31 MB** (plus a 4.7 MB WAL). The staging copy lands in **tmpfs**, so during each 6-hourly run roughly 31–70 MB of RAM is occupied by `/run/brain-backup-staging`, plus `gpg` and `rclone` process memory. `/opt/brain/data/backups` has grown to **791 MB** on disk.

`verified-volatile-backup-staging.sh` explicitly checks available tmpfs capacity before copying and **fails closed** if there isn't room:

```
available_bytes="$(( $(stat -fc '%a' -- "$root") * $(stat -fc '%S' -- "$root") ))"
(( available_bytes >= required_bytes )) || { echo "insufficient tmpfs capacity: need ... have ..." >&2; return 1; }
```

**This is a concrete, named coupling worth carrying into #319/#321:** tmpfs pages cannot be swapped out (there is no swap), so they are unreclaimable. If Life in Days ever drives the host to the point where `/run` cannot supply ~35 MB, **AI Brain's off-site backup silently starts failing** — not crashing, not alerting, just logging a refusal to a file nobody reads. That is a quieter and more dangerous failure mode than an OOM kill, and no cgroup limit on Life in Days' own unit prevents it. At current sizes (382 MB tmpfs, 896 KB used, 31 MB needed) there is a wide margin; the risk is worth stating, not worth panicking about.

## 8. Discrepancies from `IMPLEMENTATION-PLAN-POST-M6.md` §7.8

Called out explicitly rather than silently corrected, per #316's acceptance criteria.

**(a) "Two other resident products" understates it — there are eleven non-OS units and a root cron job.** §7.8 named `brain.service` and `hackathon-review.service`. It missed the seven auxiliary `brain-*` timer/service pairs and `/etc/cron.d/brain-backup` entirely. The previous session's own lesson — that `hackathon-review.service` was found only by walking `systemctl list-units` directly — repeated itself one level down: `list-units --all` plus `list-timers --all` plus `/etc/cron.d/` was needed to see the rest.

**(b) The memory figures in §7.8 and issue #277 measure a different thing than the ceiling decision needs.** §7.8 records `brain.service` at "239–240 MB RSS". That number is *correct* as main-process RSS (`ps` confirms `next-server` at 240,724 kB right now) but it is **not** the cgroup footprint, which is what a `MemoryHigh`/`MemoryMax` decision is denominated in:

| Measure for `brain.service` | Value |
|---|---|
| Main process RSS (`ps`) | **240 MB** ← the number in §7.8 / #277 |
| cgroup `memory.current` | **420 MB** |
| cgroup `memory.peak` (since boot, 74 d) | **528 MB** |
| of which `anon` (unreclaimable) | **179 MB** |
| of which `file` (page cache, reclaimable) | **230 MB** |
| `slab` | 7.4 MB |

So the honest reading is: AI Brain's **truly unreclaimable** footprint is ~**180 MB**, lower than the 240 MB §7.8 quoted; but its **cgroup accounting peak** is ~**528 MB**, more than double it. Which number is "right" depends entirely on the question — and for #321 it will matter that neither 240 MB nor 528 MB is the anon figure that survives memory pressure.

`hackathon-review.service` is even smaller than §7.8 suggested: `anon` **9.9 MB**, `file` **0**, `memory.current` 10.0 MB, `memory.peak` 10.6 MB (§7.8's "21 MB" is process RSS including shared library mappings).

`cloudflared.service`: `memory.current` 19.8 MB, `memory.peak` 35.2 MB.

**(c) §7.8's "~3.3 GB genuinely free" is close but slightly optimistic today.** Current `available` is **3.0 GiB**; `system.slice` holds `anon` 275 MB and `file` 1.46 GB (`memory.current` 1.85 GB), the bulk being reclaimable page cache. 3.0 GB available is still ample.

**(d) A third and fourth Cloudflare ingress hostname exist.** §7.8 described "one ingress list"; the active list has **four** entries, not two:

```
brain.arunp.in          → http://127.0.0.1:3000
brain-staging.arunp.in  → http://127.0.0.1:3000     ← both point at the same process
hackathon.arunp.in      → http://127.0.0.1:4173
(catch-all)             → http_status:404
```

`brain-staging.arunp.in` resolving to the *same* port 3000 as production is worth knowing before anyone assumes staging is isolated. Adding a Life in Days hostname means editing this one shared file — see §10.

**(e) Docker's absence is now proven, not inferred.** Four independent checks: no `docker`/`podman`/`containerd`/`nerdctl` on `PATH`; no `/var/run/docker.sock`; **no** matching `dpkg` packages installed; no `/var/lib/docker`. `reference/HETZNER-SHARED-HOST-DEPLOYMENT-SPIKE.md`'s Docker Compose topology is not merely unused here — the runtime is absent, and introducing it would be a new dependency installed on a shared production host.

**(f) `brain-processing-audit.service` is currently in a `failed` state — a pre-existing problem in AI Brain, not caused by this audit.** Failed 2026-08-21 18:43:49 IST (≈37 min before this audit began, on its own 6-hourly schedule), `exit 1`, from `processing-readiness-prod.mjs audit --require-ready --require-production-config`. Its logged reason: `"migrationFailures":["applied_migration_not_packaged"]`, checkpoint `"code":"red"`, `"ready":false`. **This is the owner's other product's issue and is outside M0.1's scope — flagged for the owner, deliberately not touched.** It matters to M0.1 only as evidence that a failing timer-driven unit on this host can sit red for hours without anyone noticing, which is directly relevant to how M17 (System Health) should think about Life in Days' own failures.

## 10. Facts that will constrain later M0.1 tickets

Recorded here so #317–#324 don't have to rediscover them.

1. **Nine days of `sar` history already answers most of #317 without generating any load.** Real peaks under real use: 9.4% CPU, 431 MB memory, 0.34 load. A synthetic load test can only tell us what a load *we invented* costs; `sar` tells us what the neighbours actually do. #317 should lead with this and treat generated load as a supplement, not the primary evidence.
2. **`MemoryAccounting=yes` is already on** for all three long-running units, so per-cgroup `memory.current`/`memory.peak` are available for free — #319 does not need to install or enable anything to measure.
3. **No unit on this host has any cgroup limit.** All ten checked report `MemoryMax=infinity`, `MemoryHigh=infinity`, `MemoryLow=0`, `MemoryMin=0`, `CPUWeight=[not set]`, `CPUQuotaPerSecUSec=infinity`, `IOWeight=[not set]`, `TasksMax=4538`. Life in Days limiting *itself* protects the neighbours only from Life in Days; nothing protects Life in Days from them, and nothing protects anyone from the kernel's choice of OOM victim.
4. **Zero swap + tmpfs staging + no swap for tmpfs pages** is the sharpest interaction on this host (§5.1).
5. **Disk, not memory, is the nearer ceiling.** 22 GB free, and two consumers already growing without a cap: `/opt/brain/data/backups` at **791 MB** (four new encrypted snapshots a day) and **`journald` at 1.6 GB with no `SystemMaxUse` configured at all** (`/var/log` totals 1.9 GB). `/opt/brain` is 5.1 GB, `/home` 3.3 GB. A fourteen-year photo archive lands on the same 22 GB — this belongs in #322/#324's stay-or-move comparison at least as much as memory does.
6. **`unattended-upgrades` is enabled** (`APT::Periodic::Unattended-Upgrade "1"`, `Update-Package-Lists "1"`, `Download-Upgradeable-Packages "0"`). No `Automatic-Reboot` directive is set, so the default (no automatic reboot) applies — but kernel updates will therefore accumulate un-rebooted, and 74 days of uptime on a `6.8.0-124` kernel is consistent with that.
7. **Port allocation convention:** 3000 (AI Brain), 4173 (hackathon-review), 20241 (cloudflared). Everything binds `127.0.0.1` explicitly and is exposed only via the tunnel. Life in Days should pick an unused localhost port and follow the same pattern.
8. **Unit-hardening baseline to match:** `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, explicit `ReadWritePaths` (§3.1).
9. **`sysstat` retains 9 days.** If #319's experiment is to be reconstructible after the fact, its results must be written down; the raw history will roll off.
